# 대시보드에서 취약점 DB 사용하기

Workspace의 DB는 취약점 자료를 관리하는 화면입니다. Modules의 DB는 그 자료를 처리하는 모듈의 실제 상태와 기본 설정을 확인하는 화면입니다. 두 화면은 같은 서버의 `casper-db`를 사용합니다.

## 보고서 접수와 검토

1. **Workspace → DB → 보고서 접수**에서 대상 ID와 HWP/HWPX 파일을 지정합니다. 대상 ID는 **그 보고서에서 원래 점검한 사이트**의 관리 이름입니다. 새로 점검하려는 사이트를 대신 입력하지 않습니다. `vul-2`와 `vul2`는 다른 이름입니다. 같은 파일이 다른 이름으로 접수돼 있다면 기존 대상과 보고서 열기 버튼을 표시합니다.
2. 이미지에 있는 글도 읽어야 한다면 **스크린샷·이미지 안의 글자도 읽기**와 언어를 선택하고 **파일 올리고 내용 읽기**를 누릅니다. 최대 파일 크기는 32,000,000바이트입니다.
3. 접수하면 원본 파일과 추출 초안이 서버에 보관됩니다. 파일 선택 창에서 지정한 PC 경로를 사례에 저장하지 않습니다. 업로드만으로 취약점 사례가 등록되지는 않습니다.
4. 보고서 목록에는 파일명, 대상, 접수 시각, 검토·등록 상태와 후보 수가 표시됩니다. 같은 원본 파일의 여러 추출 버전은 한 행으로 묶이고 상세에서 버전을 선택합니다. 파일명이 같아도 파일 내용이 다르면 별개 보고서입니다. 과거 CLI 접수처럼 시각 기록이 없는 자료는 시각 미기록으로 표시합니다.
5. 보고서를 선택하면 ① 보고서 올리기 → ② 읽어온 내용 확인 → ③ 취약점 DB에 등록 중 현재 단계를 표시합니다. 왼쪽에는 원문·이미지·OCR 결과, 오른쪽에는 자동으로 채운 값이 나옵니다. 이미 추출된 값을 다시 입력할 필요는 없습니다. 미확정 값도 근거가 있고 하나로 정리되는 후보는 **확인용 후보**로 미리 채웁니다. 같은 값이 여러 번 나와도 화면에는 묶어서 표시하고 모든 출처를 보존합니다. 서로 다른 값·여러 Payload·미확인 값은 임의 선택하지 않으며, 후보 전체를 보관할 수 있습니다. 저장한 검토자의 수정값이 새 제안값보다 우선합니다.
6. 원문과 자동 입력 내용 및 주의사항을 비교한 뒤 **확인하고 다음**을 누릅니다. 해당 항목을 등록 대상으로 확인했다는 결정과 기본 확인 이유가 저장되고, 로그인한 검토자·실제 시각·원문 근거가 연결됩니다. 다음 취약점으로 이동하고, 마지막 항목에서는 **확인하고 DB에 등록** 버튼이 검토 저장과 실제 DB 등록을 이어서 수행하고 등록된 자료 화면으로 이동합니다. 재현에 필요한 값이 덜 추출되어도 별도 입력 없이 보고서 자료를 등록할 수 있습니다.
7. 기본 확인 화면에는 읽힌 값과 보관할 Payload가 표시됩니다. 대표 Payload를 정하지 않아도 후보 전체와 출처가 함께 등록됩니다. 아직 확정하지 않은 정보는 접힌 안내에서 확인하며 등록 전에 빈칸을 채울 필요가 없습니다. 실제로 틀린 내용을 발견했거나 대표값을 정할 때만 **틀린 내용 수정·대표값 지정 (필요할 때만)**을 펼칩니다. 목록 형식은 한 줄에 하나이고 Payload의 따옴표와 공백은 보존합니다. 별도 자료로 확인했다면 근거 위치에 `manual:확인한 자료의 설명`을 남깁니다. 판단하기 어렵다면 **보류하고 다음**을 선택합니다. **임시 저장**은 현재 편집 내용을 저장하고 이동하지 않습니다. 보류·제외·직접 작성할 검토 이유는 세부 설정에서 지정합니다. 보류한 항목은 자동 등록하지 않습니다. 확인한 항목은 필수 재현 정보가 비어 있어도 등록하며 빈 값을 임의로 채우지 않습니다. 여러 후보·출처·검토 기록도 함께 보존합니다.
8. 보류 항목이 남거나 **최종 등록 전 확인으로 이동**을 선택했다면 마지막 화면에서 준비·보류·기등록 건수를 확인하고 **확인한 N건을 DB에 등록**을 누릅니다. 부족한 항목 버튼은 해당 확인 화면으로 돌아갑니다. 여러 후보 중 일부만 준비됐으면 **확인이 끝난 항목만 등록하고 나머지는 보류합니다**을 명시적으로 선택합니다. 실제 등록이 끝나면 등록된 취약점 목록과 상세 화면으로 이동합니다. 일부만 등록한 경우에는 남은 항목을 계속 확인할 수 있도록 보고서에 머뭅니다. 최신 검토가 다른 창에서 변경됐으면 다시 읽어야 합니다.

보고서 자료 등록과 재현 준비 완료는 별개입니다. 같은 통합 SQLite DB의 `report_knowledge_records`에 추출값·미확인 값·원문 근거·검토 기록·버전이 저장되며 사례 목록과 통합 지식 조회에서 검색됩니다. 기존 `cases`의 엄격한 재현 준비 검증은 유지합니다. 정보를 보완해 검증을 통과하면 같은 ID로 재현 준비 사례가 추가되며 목록은 한 건으로 보입니다. 파서의 위치 매칭과 재현용 사례 조회는 완성된 `cases`만 사용하고, 미완성 자료는 `report_knowledge` 문맥으로 제공하며 자동 실행을 허용하지 않습니다.

예를 들어 보고서 한 파일에서 세 후보를 추출하고 두 후보를 등록했다면, 보고서 목록에는 파일 한 개가 남고 사례 목록에는 등록한 두 건이 보입니다. 새 추출 버전의 미검토 항목이 과거 등록 사실 때문에 사라지지 않습니다. 원본 문서와 초안 근거는 접수 저장소에 남습니다.

목록은 요약만 조회하며 원본 문서 바이트를 매번 읽지 않습니다. 파일명·대상 검색, 상태 필터, 정렬과 50개 단위 페이지 이동을 지원합니다. CLI로 다른 접수 작업 공간에 넣었던 보고서는 자동으로 합쳐지지 않습니다. 서버가 사용하는 접수 경로를 확인하고 기존 자료의 이관 범위를 먼저 정합니다.

다른 사이트의 보고서를 참고하려는 경우에도 원래 대상은 보존합니다. 현재 자동 사례 조회는 같은 대상의 기록을 찾는 범위이며, 다른 대상에 대한 적용 가능성을 자동 비교·재현하는 기능은 별도입니다. 다른 사이트에서 발견된 취약점을 새 사이트에서 확인된 결과로 등록하지 않습니다.

Workspace의 **보고서** 메뉴는 Agent 점검 후 생성된 결과 문서를 읽고 내려받는 곳입니다. 이곳의 생성 보고서와 DB에 입력하는 참고 보고서를 구별합니다.

## 이미지의 글자 읽기

OCR은 HWP/HWPX 읽기와 별도로 문서 안의 지원되는 내장 이미지에서 글자를 추출합니다. 서버의 Tesseract와 언어 데이터를 사용하고 외부 OCR 서비스로 보고서를 보내지 않습니다. 한국어는 `ko`, 영어는 `en`, 혼합은 `kor+eng`을 선택합니다.

Modules → DB에서 엔진·언어 사용 가능 여부를 확인합니다. OCR을 선택한 접수의 상세 화면에는 인식된 문장과 `image-ocr:이미지ID#line번호` 근거가 표시됩니다. OCR 결과는 사람의 검토가 필요한 초안입니다. 지원하지 않는 이미지나 인식 실패는 이미지별 결과에 남고 성공으로 바뀌지 않습니다.

## 로컬 LLM으로 문맥 추출과 원문 대조

기본 접수는 기존 문서 읽기·추출 규칙·선택한 OCR만 사용하며 LLM이 필요하지 않습니다. 접수 화면의 **선택 기능 · 로컬 모델로 추가 분석**을 펼쳐 **로컬 LLM으로 문맥을 읽고 원문과 대조**를 선택하면 본문·표·OCR과 해당 취약점의 원본 이미지를 함께 읽습니다. 기존 보고서는 상세의 **선택 기능 · 로컬 모델로 다시 분석**을 펼쳐 **로컬 LLM으로 다시 분석·원문 대조**로 처리합니다. 새 추출 버전은 검토 전 상태로 만들며, 기존 등록 자료·검토·원본 바이트를 덮어쓰지 않습니다. 결과의 **이 값을 뽑은 원문 근거**를 펼쳐 인용한 문장과 이미지 위치를 확인할 수 있습니다.

추출은 다음 순서로 동작합니다.

1. 파일과 이미지의 SHA-256을 확인하고 취약점별로 연결된 본문·표·OCR·이미지만 로컬 모델에 전달합니다.
2. 모델은 Payload와 실제로 기록된 재현 동작을 원문 인용과 함께 구조화합니다. 요청 방식은 보고서에 명시된 경우만 추출합니다. 보고서에 메서드가 없어도 등록할 수 있으며, 현재 점검에서는 웹 파서의 method 관찰값을 별도 출처로 사용합니다. 파서 값으로 과거 보고서의 메서드를 채워 넣지 않습니다.
3. 인용문과 추출값을 원문 문자열과 대조합니다. 모델이 인용 문장을 부정확하게 복사했어도 추출값 자체가 지정된 원문에 그대로 있는 경우에만 해당 실제 구간으로 다시 연결합니다. Payload의 따옴표·공백·인코딩은 교정하지 않습니다.
4. 별도 로컬 모델 요청으로 원문과 이미지를 다시 보고 각 후보를 대조합니다. 출처 불일치·지원되지 않는 값은 보류하며 문맥 추정은 확정값과 나눕니다. 이는 자동 검사이며, 사람이 정답을 작성해 측정한 정확도 점수와 다릅니다.
5. 통과한 후보는 입력칸에 미리 채우고 원문 근거를 붙입니다. 사람이 확인하고 다음을 누르면 검토 기록이 남고, 마지막 확인으로 기존과 같은 통합 DB에 등록됩니다.

### 실행과 개인정보 경계

모델 다운로드에는 인터넷이 필요합니다. 다운로드 컨테이너에는 보고서나 앱 데이터·API 키를 연결하지 않습니다. 이후 추론 컨테이너는 외부 포트가 없는 Docker 내부 네트워크에서 실행합니다. 보고서 클라이언트는 직접 로컬 HTTP만 허용하고 프록시·리디렉션·cloud 모델·외부 API 대체를 허용하지 않습니다. 보고서 처리 작업에는 외부 API 키를 전달하지 않습니다. `agent/.env`의 DeepSeek 키는 이 경로에서 사용하지 않습니다.

```sh
# NVIDIA GPU가 있는 Windows/Linux
node scripts/setup-report-llm.mjs --gpu
# CPU 실행은 --gpu를 생략합니다.
docker compose -p ca3p-db-workspace -f docker-compose.yml -f docker-compose.report-llm.yml up -d --build dashboard
```

로컬 모델을 사용할 경우 Modules → DB에서 연결을 확인합니다. **기본으로 로컬 LLM 문맥 추출·원문 대조**는 기본적으로 꺼져 있으며, 새 접수마다 모델 분석이 필요한 운영 환경에서만 켭니다. 현재 기본 모델은 `qwen3-vl:8b-instruct`입니다. 모델 이름·가중치 digest·프롬프트 버전·원문 및 이미지 해시·대조 결과가 추출 버전에 남습니다. 외부 API 키는 필요하지 않습니다.

Mac에서 대시보드와 Ollama를 모두 직접 실행하면 서버 환경의 `CASPER_DB_REPORT_LLM_URL=http://127.0.0.1:11434`, `CASPER_DB_REPORT_LLM_MODEL=qwen3-vl:8b-instruct`를 사용합니다. 추론 프로세스의 외부 통신을 운영 환경에서도 차단해야 합니다. Docker 내부 네트워크 방식은 CPU로도 실행할 수 있습니다. Mac의 실제 하드웨어 성능은 별도 확인이 필요합니다.

분석은 취약점 한 건당 이미지 4개·본문/OCR 40,000자 이내로 제한합니다. 모델 연결 실패·출력 잘림·문맥 한도 도달 시 오류로 끝내고 원본·기존 검토는 유지합니다. 다른 제공처로 보고서를 전송하거나 미확인 값을 만들어 채우지 않습니다.

## 외부 취약점 정보

**Workspace → DB → 외부 취약점 정보**에는 같은 통합 DB에 저장된 NVD·GitHub 권고가 표시됩니다.

- 전체 목록은 CVE·GHSA·제품명 등의 검색과 제공처 필터를 지원합니다.
- 대상 ID, 패키지 생태계, 제품명과 버전을 입력한 뒤 **저장된 권고에서 조회**하면 이미 저장된 정보만 검색합니다. 네트워크 수집은 하지 않습니다.
- **공식 API에서 수집·저장**하면 기존 수집기가 GitHub의 패키지·버전 검색, 발견한 CVE에 대한 NVD 조회, 필요한 CPE·제품명 후보 검색을 수행합니다. CVE를 미리 알 필요가 없습니다. 예: 생태계 `pip`, 제품명 `jinja2`, 버전 `3.1.4`.
- 직접 입력한 제품은 사용자 제공 정보(`declared`)로 다룹니다. 파서가 직접 관찰한 설치 사실로 바꾸지 않습니다. 버전 범위가 맞아도 대상 서비스에서 공격이 성공했다는 뜻은 아닙니다.
- 수집 결과에는 요청 수, 저장 여부, 제공처별 완료 상태와 오류가 나옵니다. `partial`은 일부 검색 실패·잘림이 있는 결과입니다. 빈 결과만 보고 취약점이 없다고 판단하지 않습니다.
- 외부 제공처에는 공개 제품 식별 정보만 보냅니다. 보고서 내용, 대상 URL, 원문 근거와 로컬 파일 경로는 전송하지 않습니다.

기존 파서·Agent 연동은 그대로 유지합니다. 이 화면의 수동 입력과 기본 설정이 모든 Agent 실행 방식에 자동 적용되는 것은 아닙니다.

## DB 운영 상태와 설정

**Modules → DB**에서 실제 DB 연결·스키마, 보고서·사례·권고 수, pyhwp 설치, Tesseract와 언어 가용 여부를 확인합니다. 소스 버전만 보고 연결 상태를 정상이라고 표시하지 않습니다.

관리자는 기본 OCR 사용·언어, 권고 제공처, 최대 페이지·요청 수·수집 시간을 저장할 수 있습니다. 설정은 **대시보드의 다음 접수와 수동 권고 수집**부터 적용됩니다. 진행 중인 작업과 과거 실행의 스냅샷을 변경하지 않습니다. 다른 창이 먼저 저장한 설정은 revision 충돌로 보호합니다.

DB 경로·Python·Tesseract 실행 경로·인증 정보는 서버 배포 설정으로 관리합니다. 브라우저에서 임의 파일 경로나 SQL을 실행하는 기능은 제공하지 않습니다. 조회 계정은 자료·상태를 읽을 수 있고, 접수·검토·등록·설정 변경·외부 수집은 관리자만 수행합니다.

최근 수집과 접수·검토·사례 변경의 감사 로그도 표시합니다. 수집의 `running`은 완료 기록이 없는 상태이며 강제 종료된 작업도 포함할 수 있습니다. 자동 성공이나 자동 재개를 의미하지 않습니다.

## 로컬 Docker로 확인하기

Docker Desktop의 Linux 엔진을 실행한 뒤 저장소 루트에서 실행합니다.

```sh
docker compose -p ca3p-db-workspace up -d --build dashboard
docker compose -p ca3p-db-workspace exec dashboard cat /app/.runtime/access.txt
```

`http://127.0.0.1:4173`을 열고 출력된 관리자 계정으로 로그인합니다. 계정 정보는 공유하거나 커밋하지 않습니다. `-p`의 프로젝트 이름에 따라 DB·원본·로그·인증 자료용 볼륨이 달라지므로 항상 같은 프로젝트 이름으로 실행합니다. 처음 시작하는 프로젝트는 빈 DB로 시작합니다.

Dockerfile에는 Python, pyhwp, Tesseract와 한국어 데이터가 포함됩니다. UTF-8 로케일을 지정해 한글 다운로드 파일명도 보존합니다. `CASPER_DB_PATH`는 사례·공개 권고·공격 정보를 저장하는 통합 DB이고, `CASPER_DB_INTAKE_WORKSPACE`는 원본·추출·검토 기록을 보관하는 접수 작업 공간입니다. 같은 경로·볼륨을 유지해야 재시작 후 같은 자료가 보입니다.

확인 순서는 보고서 접수 → 원문·OCR 확인 → 검토 저장 → 사례 등록 → 목록 조회 → 외부 권고 수집·조회 → Modules DB 상태 확인입니다. 공개 시험 문서와 실제 보고서를 구분하고 보안 보고서는 승인된 서버에서만 사용합니다.

```sh
docker compose -p ca3p-db-workspace restart dashboard
docker compose -p ca3p-db-workspace logs --tail=50 dashboard
```

재시작 후 같은 자료가 남는지 확인합니다. `down -v`는 볼륨과 자료를 제거하므로 일반 종료에는 사용하지 않습니다. macOS 직접 실행과 Linux 컨테이너 실행, Apple Silicon 하드웨어 확인은 각각 별도의 검증입니다.

## 최신 모듈과 함께 사용할 때

현재 웹 파서의 `web-parser-1` TargetInfo와 기존 `3.4`·`structure-1.0` 결과를 DB 어댑터에서 함께 받습니다. 현재 형식에서는 실제 리소스 요청의 메서드·쿼리 이름과 폼에 선언된 메서드·필드 이름만 옮깁니다. 단순 링크만으로 요청 방식이나 POST 본문을 만들어 넣지 않습니다. 다른 원점의 요청은 현재 대상의 과거 사례 위치로 사용하지 않습니다.

Wappalyzer의 제품·라이브러리 탐지는 설치 확정이 아닌 단서(`indicator`)입니다. 공개 패키지 생태계를 알 수 없는 이름은 CPE/제품 후보 검색에 사용하며, npm·pip 패키지 이름으로 임의 변환하지 않습니다. GitHub 패키지 검색에는 생태계·패키지를 명시한 inventory 또는 기존 의존성 결과가 필요합니다. 입력이 잘리거나 제품 탐지가 불완전하면 그 상태를 수집 결과에 남깁니다.

제품 정보가 없어도 등록된 보고서 자료를 조회할 수 있습니다. 자료의 후보·미확정 값과 현재 파서의 관찰값은 구분하며, 자료 등록이 공격 실행 허용이나 취약점 확인을 뜻하지 않습니다. 새 `attack-tool`의 권한·실행·검증 계약은 유지하고, 보고서에서 읽은 Payload를 실행 템플릿으로 자동 승격하지 않습니다.

기존의 작업 공간 AI 채팅과 보고서 문맥 분석은 별도 기능입니다. 채팅에서 모델을 선택해도 보고서 접수의 선택 모델이나 기본 사용 설정을 바꾸지 않습니다. 보고서 접수의 기본 경로는 모델을 호출하지 않습니다.

장치 백업 검증은 기존 실행·채팅 DB와 공격 카탈로그·공개 권고의 검사를 유지하면서 보고서 자료와 버전 테이블도 허용하고 열을 검사합니다. 보고서 테이블은 해당 기능을 초기화하거나 자료를 등록할 때 만들며, 기존 사례 DB를 단순 이전할 때 불필요하게 추가하지 않습니다. 원본 파일과 검토가 들어 있는 별도 접수 DB도 SQLite backup 방식으로 함께 보관해야 합니다.
