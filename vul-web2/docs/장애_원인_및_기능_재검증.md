# Docker 장애 원인 및 두 대학 사이트 기능 재검증

- **검증일:** 2026-10-20 (KST)
- **현재 상태:** Docker Desktop와 두 사이트 컨테이너 정상 기동

## 1. 장애 원인과 조치

이전 Docker Desktop 4.65.0의 백엔드 로그에는 `initializing Inference manager` 과정에서 `dockerInference` AF_UNIX 소켓을 제거하지 못해 시작이 중단됐다는 오류가 남아 있다. 이 때문에 Linux 엔진 파이프에 연결할 수 없었고 두 사이트 컨테이너도 종료됐다. 로그만으로 Windows가 해당 소켓을 놓지 못한 내부 원인까지 확정할 수는 없다. [Docker의 동일 오류 이슈](https://github.com/docker/desktop-feedback/issues/460)에는 같은 메시지가 기록돼 있으며, Docker 담당자는 수정이 Desktop 4.92 이상에 포함돼야 한다고 밝혔다.

사용자가 Docker Desktop을 **4.95.0**으로 업데이트한 뒤 `docker desktop status`는 `running`, `docker info`의 서버 버전은 **29.8.2**였다. 새 백엔드 로그에서는 `dockerInference` 소켓 수신이 성공했다. 기존 `ca3p-universities_daehan-data`와 `ca3p-universities_wonchang-data` 볼륨은 남아 있었고, `docker compose up --build -d`로 두 이미지를 재빌드하고 컨테이너를 다시 기동했다. 볼륨 초기화나 공장 초기화는 하지 않았다.

별도 코드 점검에서는 `npm start`에 공통 `PORT` 환경변수를 전달하면 두 자식 서버가 같은 포트로 실행되는 충돌도 발견했다. `scripts/start-both.mjs`에서 대한대학교는 `DAEHAN_PORT`(기본 4101), 원창대학교는 `WONCHANG_PORT`(기본 4102)를 사용하도록 수정했다. 이 코드 문제는 위 Docker Desktop 백엔드 장애의 원인은 아니다.

## 2. 재검증 결과

| 항목 | 수행 방법 | 결과 |
| --- | --- | --- |
| 소스 구문과 Compose 설정 | 서버·DB·검사 스크립트 `node --check`, `docker compose config --quiet` | 통과 |
| 두 서버의 동시 직접 실행 | 메모리 DB, 임시 포트 18081·18082, 공통 `PORT`도 설정한 상태로 `npm start` | 두 홈페이지와 CSS·JavaScript 응답 200, 종료 후 포트 해제 |
| 기능·취약 동작 | `npm run smoke`로 각 사이트를 메모리 DB에서 구동 | 두 사이트 모두 통과 |
| Docker 기동 | `docker compose up --build -d`, `docker compose ps` | 서로 다른 이미지·컨테이너, 양쪽 `healthy`, 호스트 바인딩 127.0.0.1:4101·4102 |
| 실제 배포 기능 | `node scripts/deployment-check.mjs` | 두 사이트 모두 통과 |

메모리 DB 검사는 각 사이트의 13개 공개 페이지, 자산, 공지·대학소식 상세, 검색·페이지 이동, 로그인·로그아웃, 문의 생성, 역할 제한, 부속 업무 조회와 오류 경로, 관리자 게시글 작성·수정·뉴스 등록·일정 가져오기를 확인했다. 의도된 IDOR, SQL 주입, 무인증 삭제 후 홈 500 등 대표 취약 동작도 기존대로 재현했다. 두 사이트의 직접 외부 의존성 집합이 서로 다른지도 검사했다.

배포 검사는 **기존 볼륨의 게시글·문의·일정을 변경하지 않는 경로**로 진행했다. 각 사이트의 13개 공개 페이지, CSS·JavaScript·캠퍼스 이미지, 게시판 상세, 검색, 학생·담당자·관리자 로그인과 역할 제한, 부속 업무의 본인 목록·상세 및 타 담당자 건 조회, 관리자 읽기 화면, 로그아웃을 확인했다. 가상 계정 로그인으로 메모리 세션만 생성했다.

## 3. 검증 범위

지속 DB에서 작성·수정·삭제를 반복하면 운영 중인 더미 콘텐츠가 바뀌므로, 그 흐름은 메모리 DB에서 검증했다. A09 보안 이벤트 기록·경보는 코드상 부재를 확인했지만 운영 로그와 경보의 동적 동작은 검증하지 않았다. 장시간 부하나 모든 예외 입력의 시험도 범위에 포함하지 않았다. 취약점별 판정과 평가 가정은 [사전 침해분석 및 취약점 보고서](사전_침해분석_및_취약점_보고서.md)에 기록돼 있다.
