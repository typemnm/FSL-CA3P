# 대시보드 재구성 계획

기준: `develop`에서 분기한 `1mn2147/dashboard_update` · 작성일: 2026-10-28

## 1. 목표와 현재 경계

대시보드를 **취약점 점검 작업공간(Workspace)**과 **모듈 운영 화면(Modules)**으로 재구성한다. 사용자는 공격 대상을 선택하고 실행·이력을 확인하며, 보고서를 화면에서 읽고 내려받고, 취약점 DB의 보고서 접수부터 사례 관리까지 수행한다. 운영자는 각 모듈의 유효 설정과 로그를 확인하고 지원되는 설정을 변경한다.

현재 프론트엔드는 `agent-dashboard/dist/`의 정적 단일 페이지이며, 시작·실시간 이벤트·이력·리포트·비교·CI·통합 상태가 별도 해시 화면에 흩어져 있다. 중앙 API에는 실행 생성/목록/상세/중지, 실행 이벤트, 모델 목록, 플랫폼 상태, 실행 비교, JSON 결과 및 조건부 HWPX 다운로드가 있다. 따라서 첫 단계에서 이 기능을 새 정보 구조로 옮길 수 있다. 아래의 **보고서 원문 미리보기**, **DB 접수/수정/삭제**, **모듈 설정 저장과 독립 로그 조회**는 중앙 API 연결을 추가해야 완료된다. 화면만 만든 상태를 기능 완료로 취급하지 않는다.

현재 실행 대상은 등록된 `vul-web-1`, `vul-web2-daehan`, `vul-web2-wonchang` 실습 대상이다. 대학 실습은 허용된 내부 원점을 입력할 수 있지만 임의 외부 URL 실행은 아직 지원하지 않는다. **이번 업데이트의 목표 범위에는 등록 없이 임의의 외부 URL을 입력해 실제 점검하는 흐름을 포함한다.** 이는 새 입력창만으로 구현할 수 없으므로 별도 외부 대상 실행 계약과 런타임·모듈 검증 경로를 추가한다. `core-fixture`에 입력하는 URL은 표시용이므로 외부 대상 입력과 분리한다.

## 2. 정보 구조와 이동 경로

### 화면 골격과 공통 UI

- 데스크톱은 고정 사이드바, 상단 상태/계정 바, 페이지 제목·설명, 페이지별 보조 탭, 본문 순서로 구성한다. 공격 실행 화면은 설정 패널과 실시간 결과를 분리하고, 목록 화면은 검색/필터와 결과를 한 화면에서 조작하게 한다.
- 좁은 화면에서는 사이드바를 키보드로도 여닫을 수 있는 메뉴로 바꾸고, 표는 핵심 열만 남긴 카드/가로 스크롤 뷰를 제공한다. 로그·증거·보고서 본문은 읽기 영역의 폭을 확보한다.
- 상태 색상과 라벨을 함께 사용하고, 시간은 기준 시간대를 표시한다. 로딩·빈 결과·권한 없음·처리 실패·연결 끊김을 서로 다른 화면 상태로 정의한다.
- 공통 컴포넌트는 대상 선택기, 실행/문서 상태 배지, 필터 가능한 표, 이벤트 타임라인, 증거 뷰어, 로그 뷰어, 업로드 영역, 변경 확인 대화상자다. 모든 주요 조작은 키보드·스크린리더와 모바일에서 사용할 수 있게 한다.
- 필터·선택된 실행·상세 탭은 URL과 동기화하고, 실행·보고서·DB의 원본 데이터는 서버에서 다시 읽는다. 로컬 저장소는 테마나 접힌 메뉴처럼 개인 표시 설정에만 사용한다.

## 3. Workspace 화면

### 3.1 공격

**새 점검**은 `대상 유형과 URL → 대상 사전 점검 → 검사 방식·모델 → 실행 조건 확인 → 시작` 순서로 구성한다.

- 대상: `등록 실습 대상`과 `외부 URL`을 분리한다. 실습 대상은 목록에서 선택하고, 외부 대상은 시작 URL(`http`/`https`, 경로 포함), 표시 이름과 허용 원점·경로 범위를 입력한다. URL을 저장 없이 바로 점검할 수 있다. 외부 URL은 실제 접속 대상임을 명시하고, 표시용 fixture URL과 혼동하지 않게 한다.
- 사전 점검: 서버가 URL을 정규화하고 DNS·TLS·연결 상태, 리다이렉트, 허용 범위와 사용 가능한 검사/모델을 확인한다. `검증 중`, `준비 완료`, `접근 실패`, `범위 거부`, `지원 검사 없음`을 구분한다. 접속 실패와 검사 미지원은 서로 다른 원인으로 보여준다. 동일 원점이 기본 범위이며 경로 범위는 사용자가 더 좁힐 수 있다.
- 검사 방식: 실습 대상의 `범용 취약점 점검`, `기존 단일 검사`, `코어 fixture`와 외부 대상의 `외부 대상 탐색·점검`을 구분한다. 외부 대상에서는 fixture 전용 XSS/IDOR 검사와 고정 계정을 제공하지 않는다. 첫 외부 범위는 비인증 공개 페이지의 제한된 읽기 관찰이다. 독립 검증기를 연결한 유형에만 해당하는 능동 검사를 활성화하며, 지원 검사·모델 필수 여부, 결과의 의미와 HWPX 생성 가능 여부를 방식별로 표시한다. 검증기가 없으면 관찰 전용으로 표시하고 취약점 확정을 주장하지 않는다.
- 모델: 현재 사용 가능한 모델만 선택하고 사용 불가 이유를 설명한다. 유료 모델 호출이 필요한 실행에는 실행 전 비용 발생 가능성과 요청 예산을 보여준다.
- 조건 확인: 정규화된 실제 대상, 허용 원점·경로·메서드, 접근 방식, 요청·시간·반복 예산, 적용 정책 버전, 모델 비용과 중지 방법을 보여준다. 외부 대상에는 해당 대상의 점검 권한 확인을 받는다. 사용자가 정책 밖의 명령을 넣는 입력란은 만들지 않는다.
- 실행: 관리자/운영자에게만 시작·중지 조작을 제공하며, 서버가 권한·사전 점검 결과·실행 범위를 재검증한다. 중복 클릭 방지, 로딩, 실패 재시도, 연결 끊김 상태를 분리한다.

**진행 중 실행/상세**는 실행 상태, 대상·방식·모델, 시작/종료 시각, 가변 단계 이벤트, 모듈별 요청·응답과 guardrail 판정, 가설·검사·증거 수, `findings[]`, 미점검 범위와 종료 사유를 보여준다. 외부 실행에는 `외부 대상` 배지, 정규화 URL, 당시 scope·정책·모듈 버전, 실제 접속 여부를 표시한다. 범위 밖 링크·리다이렉트는 자동으로 범위를 넓히지 않고 거부 사유를 이벤트에 남긴다. DNS 주소가 바뀌면 허용 가능한 공개 주소인지 다시 확인하고 재검증 실패를 기록한다. `confirmed`, `not_reproduced`, `inconclusive`, `not_tested`를 구분하고 지원 검증기가 없는 후보를 확정 finding으로 표시하지 않는다. 접속 불가·부분 완료·취소도 구별한다. SSE가 끊기면 재연결/조회로 복구하고 새로고침 후 서버의 실행 상태를 다시 읽는다.

**실행 이력**은 대상 유형/URL, 방식, 상태, 모델, 기간, finding 판정으로 검색·필터·정렬한다. 행을 열면 당시 설정과 증거를 포함한 동일한 상세 화면으로 이동한다. **실행 비교**는 기존 비교 기능을 옮기며 기준/후보 실행의 대상 URL뿐 아니라 경로 범위·접근 방식·정책·환경·모델·모듈 digest 차이를 먼저 표시해 비교 가능 조건을 알린다.

### 3.2 보고서

목록의 기본 단위는 실행이다. 한 실행에 여러 확정 finding이 있으면 문서가 finding별로 묶여 보이도록 한다. 대상·일자·실행 방식·판정·문서 상태로 검색하고, 실행 상세 및 관련 DB 사례로 이동할 수 있다. 외부 대상 보고서는 실습 보고서와 구별하고 당시의 정규화 URL·허용 범위·실제 접속 여부·지원/미지원 검사와 미검증 사유를 명시한다.

상세 화면에는 실행 JSON의 전체 결과·증거·finding·coverage를 읽기 쉬운 섹션으로 렌더링한다. 생성된 HWPX의 **완성 문서 내용**도 브라우저에서 읽을 수 있도록 인증된 HTML 또는 PDF 미리보기 경로를 추가한다. 요약 카드만 보여주는 것을 원문 읽기로 간주하지 않는다. 원본 HWPX 및 JSON은 별도 버튼으로 내려받는다. 미리보기와 다운로드는 같은 실행/finding 연결과 무결성 검사를 사용한다.

문서 상태는 `생성 중`, `다운로드 가능`, `생성 실패`, `해당 없음`으로 표시한다. HWPX가 없는 기존 실행과 생성 대상이 아닌 실행은 이유를 알려준다. 보고서 생성 오류가 finding 판정을 바꾸지는 않는다.

### 3.3 DB — 취약점 자료 관리

이 화면은 `casper-db`의 **보고서 접수**와 **취약점 사례(Case)**를 관리한다. 실행 이력 저장소와 모듈 운영 설정은 이 메뉴의 대상이 아니다.

1. **보고서 접수**: 드래그 앤 드롭/파일 선택, 대상 지정, 업로드 진행률, 확장자·크기·중복 검사. 현 파서가 지원하는 HWP/HWPX와 32 MB 상한을 우선 적용한다. PDF는 파서가 지원될 때 추가한다.
2. **초안 검토**: 추출된 취약점별 후보 필드, 원문 위치·OCR 근거, 누락·미확정 값, payload 변형을 나란히 보여준다. 검토자는 필드를 보완하고 각 항목을 수락/제외/보류한다. 원본 초안은 보존한다.
3. **등록**: 검토·검증 결과를 표시한 뒤 명시적인 등록 조작을 받는다. 등록 가능한 항목과 보류 항목을 구분하고, 중복·충돌·실패 이유를 반환한다. 업로드 완료만으로 Case를 자동 생성하지 않는다.
4. **사례 관리**: ID, 대상, 취약점 유형, URL/경로, 심각도, 상태, CVE/출처, 등록·수정일로 검색·필터한다. 상세에서는 현재 값, 근거, 원본 접수 건, revision 및 변경 이력을 본다. 편집은 revision 확인을 거쳐 새 버전으로 저장한다.
5. **삭제**: 접수 초안 제거와 등록 Case 제거를 별도 조작으로 둔다. 등록 Case는 기본적으로 보관 처리하여 일반 검색/Agent 조회에서 제외하고, 관리자에게 복구·감사 기록을 제공한다. 원본 영구 삭제가 필요하다면 별도 정책과 권한을 정한 후 구현한다. 과거 실행의 증거와 스냅샷은 소급 변경하지 않는다.

외부 권고 데이터는 별도 읽기/검색 탭으로 연결하되, 접수 보고서 Case와 출처를 혼동하지 않게 한다.

## 4. Modules 화면

`Modules` 개요는 활성 모듈, 버전/해시, 최근 상태 확인, 최신 CI 통합 테스트, 배포 소스 SHA와 연결 상태를 모아 보여준다. 각 모듈 페이지는 공통으로 `상태 → 현재 유효 설정 → 변경 이력 → 로그 → 관련 실행` 탭을 갖는다. 설정은 서버가 지원하는 필드만 편집 가능하게 하고, 저장 전에 스키마 검증·영향 범위·적용 시점을 표시한다. 변경은 새 실행부터 적용하며 진행 중/과거 실행의 manifest와 digest는 보존한다.

| 모듈 메뉴 | 설정·상태의 주요 내용 | 로그와 연결 |
| --- | --- | --- |
| Attack Module | 활성 executor, 허용 대상/메서드, 요청·시간 예산, 버전 | 전송 성공/실패, 제한/취소, 실행 ID |
| Web Parser | 수집 범위·페이지/시간 한도, 브라우저 가용 상태, 출력 계약 버전 | 관찰 단계, 수집 오류, 실행 ID |
| Guardrail | 활성 규칙·revision, 허용 범위, 예산, 판정 통계 | 허용/차단 사유와 연결된 요청·실행 ID |
| LLM | provider/모델 목록, 가용성, 기본 모델, 호출 한도·예산 | 호출 상태, 지연·토큰 사용량, 오류, 실행 ID |
| DB | `casper-db` 스키마/연결, OCR 가용성, 외부 권고 동기화 설정 | 접수·검토·등록·동기화 작업 결과 |

메뉴 이름은 **Web Parser**로 쓰되 현재 물리 디렉터리와 통합 manifest의 `xss-parser` 표기를 모듈 ID/어댑터 계약과 맞춰야 한다. 이름만 바꾸고 잘못된 상태를 보여주지 않는다. LLM 비밀키는 입력/교체만 가능하게 하고 응답·로그·화면에는 원문을 반환하지 않는다. 로그는 시간, 수준, 단계, 실행 ID, 요청 ID로 필터하고 민감 정보 마스킹과 보관 기간을 적용한다. 현재 실행 이벤트로 가능한 모듈별 조회와, 추가 수집이 필요한 서비스/작업 로그를 구분한다.

## 5. 필요한 서버 계약

아래 경로는 **제안**이다. 최종 이름·스키마는 기존 `apps/api` 및 `packages/contracts` 규칙에 맞춰 정한다.

| 영역 | 제안 계약 | 핵심 조건 |
| --- | --- | --- |
| 외부 대상 사전 점검 | `POST /api/targets/preflight` | 시작 URL 정규화, 연결·DNS/TLS·리다이렉트·범위 검사, 가능한 검사 목록과 만료되는 확인 토큰 반환 |
| 공격 | 기존 `/api/runs`, `/api/runs/:id`, 이벤트·중지·비교 API 확장 | `external-general` 유형과 외부 대상·범위·사전 점검 확인 토큰을 받고, 서버 측 권한·예산 검증 및 이력 필터/페이지네이션 지원 |
| 보고서 | `GET /api/runs/:id/report-preview/:findingId` | 인증, 실행과 문서 연결·무결성, 안전한 HTML/PDF 응답 |
| DB 접수 | `POST /api/db/intakes`, `GET /api/db/intakes/:id`, `PATCH /api/db/intakes/:id/review`, `POST /api/db/intakes/:id/publish` | multipart 크기/형식/해시 검증, stage→review→publish, 결과·오류 구조화 |
| DB 사례 | `GET /api/db/cases`, `GET/PATCH/DELETE /api/db/cases/:id`, `GET /api/db/cases/:id/versions` | 검색/페이지네이션, revision 충돌, 보관/복구, 감사 기록 |
| 모듈 | `GET /api/modules`, `GET/PATCH /api/modules/:id/config`, `GET /api/modules/:id/logs` | 읽기/쓰기 권한, 설정 revision, 검증·적용 상태, 실행 ID 연계 |

외부 대상 실행은 기존 fixture 선택 필드에 URL만 끼워 넣지 않는다. `packages/contracts`에 외부 대상 유형과 시작 URL·허용 원점/경로·접근 방식·예산·사전 점검 결과를 명시하고, `apps/application`에서 실행을 만들며, `apps/worker`의 외부 대상 런타임이 실제 접속한다. run manifest에는 정규화 대상, 범위, 연결 결과, 적용 정책·검증기·모듈 digest를 고정한다. 인증 정보나 민감한 URL 매개변수는 기록에서 마스킹한다. 현재 Case 스냅샷의 fixture ID 가정도 외부 대상 식별자로 바꾸거나, 과거 사례가 없음을 명시한다. 외부 대상에는 실습 환경의 실험 초기화 기능을 제공하지 않는다.

외부 HTTP 요청은 매 단계에서 대상 범위를 검사한다. 허용한 `http`/`https` URL만 사용하고, IPv4/IPv6의 내부·루프백·예약·메타데이터 주소로의 우회를 막는다. DNS 재조회 결과와 실제 연결 주소를 검증하고 범위 밖 리다이렉트와 링크를 따르지 않는다. 메서드·요청 수·시간·응답 크기 예산을 guardrail과 실행기에 함께 적용하며, 정책에 맞지 않는 요청은 전송 전에 거부 이벤트로 남긴다. 외부 페이지에서 읽은 텍스트는 모델에 대한 비신뢰 입력으로 취급한다. 기존 fixture 고정 계정·소스·검증기는 외부 대상에 재사용하지 않고, 외부용 관찰기와 독립 검증기가 지원하는 검사만 수행한다. 미지원 검사는 `inconclusive` 또는 `not_tested`와 이유를 기록한다. 외부 대상은 실습처럼 자동 초기화할 수 없으므로 초기 외부 실행은 읽기 전용이며, 상태를 바꾸는 검사는 해당 검증기·정책·복구 조건이 명시되었을 때만 별도로 활성화한다.

현재 중앙 API에 DB 관리 및 모듈 설정/로그 라우트가 없고, `casper-db`의 접수·Case 변경 기능은 주로 Python CLI/내부 서비스에 있다. API에서 이를 호출할 때 파일 경로를 브라우저로부터 신뢰하지 않고, 업로드·비동기 처리 상태와 오류를 저장한다. 삭제/설정 변경은 관리자, 점검 시작·중지는 관리자/운영자, 조회는 인증된 조회자에게 허용하는 기본 권한안을 적용한다. UI 비활성화와 함께 서버에서 강제한다.

## 6. 구현 순서

1. **공통 셸과 기존 기능 이전**: 새 사이드바·라우터·공통 목록/상세/상태 컴포넌트, 권한 표시, 모바일·키보드 접근성. 기존 해시 별칭과 비교·CI·통합 상태를 유지한다. 비대해진 `app.js`를 라우팅/상태/API/화면 단위로 분리한다.
2. **실습 공격·보고서 이전**: 기존 등록 대상의 선택·실행 상세·이력 필터·비교를 연결하고, 보고서 목록/읽기/다운로드 및 원문 미리보기 API를 추가한다.
3. **외부 대상 실행 연결**: 외부 대상 계약·사전 점검·범위 정책을 먼저 완성한 후, worker·parser·attack module·guardrail의 외부 실행 경계를 연결한다. 현재 Web Parser와 Attack Module의 로컬 주소 제한을 실습 경로에서 단순 해제하지 않고 외부 전용 프로필/클라이언트를 분리한다. 외부용 관찰/검증 도구의 지원 범위를 고정하고 실제 접속·부분 결과·차단 사유를 이력과 보고서에 표시한다.
4. **Workspace DB 완성**: 접수 업로드와 검토/등록 API, Case 검색·버전 편집·보관/복구를 연결한다.
5. **Modules 완성**: 모듈 ID 정합성, 설정 스키마/저장/감사, 모듈별 로그 수집·조회, CI/배포 상태 연결.
6. **검증**: 실습·외부 실행, 보고서·DB·모듈의 권한별 브라우저 흐름, 새로고침/재연결/오류/빈 데이터, 모바일·키보드, 기존 실행 기록과 URL 호환성을 확인한다. 외부 대상의 범위 이탈·DNS 변경·리다이렉트와 미지원 검사 처리를 검증한다. 기존 DOM/해시를 전제한 테스트는 새 화면 계약으로 갱신하고 `npm run verify`를 통과시킨다.

## 7. 완료 기준

- 사이드바에 지정한 두 그룹과 여덟 메뉴가 표시되고, 기존 모든 주요 기능에 새 위치가 있다.
- 관리자/운영자가 등록 실습 대상 또는 임의의 외부 URL을 선택해 사전 점검·조건 확인·실제 실행·중지를 끝까지 수행하고, 실행 중 이벤트와 저장된 이력·비교를 새로고침 후에도 볼 수 있다.
- 외부 실행의 시작 URL·범위·정책·실제 접속 여부가 이력과 보고서까지 일관되며, 범위 밖 링크/리다이렉트/DNS 변경은 실행 범위를 넓히지 않고 거부 이유를 남긴다. 지원 검증기가 없는 후보는 확정 finding이 되지 않는다.
- 사용자가 보고서 본문과 증거를 브라우저에서 읽고, 생성된 HWPX와 JSON을 권한에 맞게 내려받는다.
- 관리자가 HWP/HWPX를 업로드한 뒤 근거 검토·명시적 등록, Case 검색·수정·보관/복구와 버전 이력을 끝까지 수행한다.
- 각 모듈의 유효 설정, 적용 revision, 필터 가능한 로그와 관련 실행이 연결된다. 비밀값과 민감한 요청/응답은 노출되지 않는다.
- 조회자 권한으로 변경 요청이 거부되고, 운영자/관리자 조작의 감사 기록을 확인할 수 있다.
- 기존 실행·보고서·비교·CI·통합 상태가 유지되고, 지원되지 않는 실행·문서·설정은 이유가 표시된다.

## 8. 확인이 필요한 제품 결정

1. **결정됨 — 대상 범위**: 등록 실습 대상 외에 임의 외부 URL 입력과 실제 점검을 포함한다. 첫 외부 실행은 비인증 대상의 공개 범위를 기준으로 설계한다. 로그인 후 권한 비교가 필요한 검사는 테스트 계정·세션의 안전한 전달 방식과 별도 검증기가 준비되어야 활성화한다.
2. 등록 Case의 `삭제`: 이 계획은 보관/복구를 기본 동작으로 정의한다. 원본 문서의 영구 삭제 요구가 있다면 보관 기간과 과거 실행 증거와의 관계를 별도 결정한다.
3. 보고서 원문 읽기의 표시 형식: 인증된 HTML 또는 PDF 중 생성 모듈과 배포 환경에서 안정적으로 제공 가능한 형식을 선택한다. 어느 쪽이든 본문·표·이미지의 누락 없이 읽을 수 있어야 한다.
